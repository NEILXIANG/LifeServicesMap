# 数据记录与商业化探索框架

> 让"优化数据"和"商业化探索"都有依据，而不是凭感觉。

---

## 一、两个目标拆解

| 目标 | 需要什么数据 | 决策支撑什么 |
|---|---|---|
| **优化数据** | 数据本身的质量信号（覆盖、过期、错误率） + 用户行为信号（用什么、不用什么） | 下个版本改什么、补什么、删什么 |
| **商业化探索** | 用户规模、行为画像、付费意愿点、与"无追踪"定位的兼容性 | 是否做、怎么做、不做什么 |

**两条铁律**：

1. **先有记录，再有结论**——任何关于"用户喜欢 / 缺什么 / 愿不愿意付钱"的判断，**必须**先在 `data/` 里有数据支撑
2. **隐私优先**——本工具定位是"新移民生活服务"，用户对就医 / 办身份 / 家庭地址敏感。**不收集个体行为、不上 cookie、不跨境传输用户数据**

## 二、要记的 5 大类

### A. 访问层（自动化）—— **已就位**

| 数据 | 来源 | 频率 |
|---|---|---|
| 请求数 / 错误率 / 地理分布 / CPU 时间 | Cloudflare Workers Metrics | 实时，**24-48 小时后才有真实数据** |
| 浏览量 / 来源 / 设备 / 加载性能 | Cloudflare Web Analytics（建议接入，零成本、一行 JS） | 实时 |

### B. 用户行为（手工 + 半自动）—— **本周待补**

这些**不上传服务器**，由人工从「我自己的设备使用记录 + 群聊截图 + 主动反馈」里收集：

| 数据 | 怎么记 | 价值 |
|---|---|---|
| **搜索关键词 Top 10** | 截图本地浏览器历史里搜过的词，按周汇总 | 最值钱——直接告诉你用户缺什么地点 |
| **筛选组合 Top 5**（区域×分类）| 看哪几个组合最常被一起选 | 决定默认值 / 预设的取舍 |
| **收藏次数** | 收藏地点的分类分布 | 哪些分类 = 核心刚需 |
| **公交查询次数** | 在公交面板停留/操作次数 | "接驳"是不是高频痛点 |
| **语言切换率** | 进入时非默认语言的比例 | 决定翻译投入回报 |

### C. 数据质量（每周手工审）

| 数据 | 怎么记 | 价值 |
|---|---|---|
| 待修复条目 | 用户报错或自查发现的错误 | 数据准确性是产品信任的根本 |
| 待补充区域 | 已知缺哪些分类 / 地点 | 下个迭代的明确清单 |
| 已过期信息 | `v` 字段超过 6 个月没核实的地点 | 法律风险 + 用户信任损失 |
| 注释更新 | `note` 字段是否有误导或过时 | |

### D. 用户反馈（人工收集）

| 数据 | 来源 |
|---|---|
| 微信群截图 / 转发 | 群里有人提到工具时的截图 |
| 邮件反馈 | CITY.contact 收到的反馈 |
| 私信 | 朋友 / 群友主动联系 |
| 公开评分 | 若做了 Reddit / App 评分收集 |

### E. 运营动作（每次记）

| 数据 | 时机 |
|---|---|
| 版本变更 | `DATA_VERSION` 变化时 |
| 部署时间 | 每次 push 到 Cloudflare 后 |
| 推广动作 | 哪个群 / 帖 / 渠道 / 用了什么文案 / 带来的 UV（24h 后从 Metrics 读） |

## 三、用什么工具记

按推荐度排序（对你这个项目的实际情况）：

### 方案 1（**首推**）—— Markdown + Cloudflare

- 文件全部在 `data/` 目录，**git 版本化**（天然带时间线）
- Cloudflare Metrics / Web Analytics 截图归档
- 优点：零成本、零依赖、可回溯、可对比
- 缺点：手工汇总成本高 → **建议每周 30 分钟固定动作**

### 方案 2 —— 飞书多维表格 / Notion database

- 适合需要多人协作 / 跨设备访问 / 表格视图
- 优点：可视化好、可协作、免费额度大
- 缺点：要登录第三方平台

### 方案 3 —— 自建埋点

- **不推荐**。合规风险 + 工程成本 + 与定位冲突。除非用户量到 10K+ 月活才考虑。

```
data/

└── business-hypothesis.md     ← 商业化假设与验证记录
```

## 五、立即要做的两件事

### ① 接 Cloudflare Web Analytics（一行 JS，零成本）

1. 打开 https://www.cloudflare.com/web-analytics/
2. 用 Cloudflare 账号登录 → 点 **Add a site** → 输入 `kamloops-lifemap.neilxiang.workers.dev`
3. 拿到一段 `<script defer src="…"></script>` 代码
4. 把这段代码粘到 `src/engine.html` 的 `</body>` 前一行
5. 重新 build + 部署

接入后能看：PV、来源（搜索/社交/直链）、设备分布、加载性能、**无需 cookie、无需用户同意**。

### ② 第一次填充记录（本周内）

1. 去 Cloudflare Workers Dashboard → kamloops-lifemap → Metrics → **截图存档**到 `data/analytics-log.md`
2. 自己用一次应用，把所有筛选组合走一遍 → 写到 `data/data-quality-log.md` 的「自查清单」
3. 把 `README.md` / `CHANGELOG.md` / `上线发布包.md` 各段提到的"已知保留问题"复制到 `data/data-quality-log.md` 的「待优化清单」

## 六、商业化探索的判断维度（先记假设）

> **明确声明**：本工具当前定位是**社区公益性质**，不在产品中插入广告 / 数据销售 / 个体追踪。商业化路径**优先考虑** B2B（机构合作）而非 B2C（用户付费）。

### 可能的路径（按"与定位的兼容性"排序）

| 路径 | 与定位的兼容性 | 门槛 | 验证信号 |
|---|---|---|---|
| **政府 / NGO 合作** | ✅ 高 | 找到合适的对接人 | 一旦有机构愿意"基于这个工具做衍生版" → 立即验证 |
| **企业雇主 / 学校采购**（付费给新员工 / 学生做本地介绍） | ✅ 高 | 找到 HR / 国际学生部 | 任何一次"你这个能不能给我做个定制版"的咨询 |
| **API / 数据集授权**（图书馆 / 其他城市复用 `data-kamloops.js`） | ✅ 中（已部分支持，`export-open.py`） | 有需求方 | 有第三方主动问"能不能给我 raw data" |
| **打赏 / 捐赠**（Ko-fi / 微信打赏） | ✅ 高 | 用户量到 1000+ 月活 | 单月有 5+ 笔任意金额 → 验证核心用户存在 |
| **付费高级功能**（导出 Excel / 路线规划 / 提醒） | ⚠️ 中 | 需要重做 | 任何用户主动说"我愿意付钱加 XX 功能" |
| **广告** | ❌ 低 | — | **不建议**——与定位冲突 |

### 验证机制

任何商业化路径**必须**先在 `data/business-hypothesis.md` 写一份假设卡：

```
## 假设 [编号]：[一句话假设]
- 目标用户：[具体到一类人 / 机构]
- 价值主张：[他们为什么愿意付 / 接受]
- 验证信号：[什么行为 = 这个假设成立]
- 证伪信号：[什么行为 = 这个假设不成立]
- 最小验证成本：[不需要做什么就能判断？]
- 状态：未验证 / 验证中 / 成立 / 不成立
```

## 七、日常节奏（建议）

| 频率 | 动作 | 时长 |
|---|---|---|
| **每周日** | 填 `analytics-log.md` + 扫一遍 `feedback-log.md` | 30 分钟 |
| **每两周** | 走一遍数据自查 → 填 `data-quality-log.md` | 1 小时 |
| **每月底** | 回头看 `business-hypothesis.md`，更新状态 | 30 分钟 |
| **每季度** | 综合分析 + 决定下季度方向 | 2 小时 |
| **每次部署** | 把 `DATA_VERSION` 和部署时间写到 `analytics-log.md` 当前周那一节 | 1 分钟 |

## 八、关键提醒

- **不要陷入"为了记录而记录"**——30% 的精力花在"是否值得继续记"上。如果一周下来 `analytics-log.md` 没什么增量，先问"是数据没变，还是我在记没用的东西"
- **记录什么 vs 不记录什么**，每季度回顾一次。砍掉不用的列比新增字段重要
- **第一版可以简陋**——能写下来的就比脑子里记的强。后期再优化格式
