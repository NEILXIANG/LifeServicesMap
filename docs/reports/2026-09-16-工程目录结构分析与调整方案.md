# 工程目录结构：现状分析与调整方案（只出方案，未修改）

日期：2026-09-16 · 范围：除 `docs/` 之外的全部工程文件

`docs/` 已在今天整理完毕，这份只谈代码、脚本、构建产物和资源文件。

## 一、现状

根目录有 **28 个散文件**。按用途分一下就能看出问题：

| 类别 | 文件 | 说明 |
|---|---|---|
| 部署与构建（必须在根） | `wrangler.toml`、`worker.js`、`build.py`、`deploy.sh` | wrangler 约定配置在根；build/deploy 是最常敲的两条命令 |
| 校验与测试（6 个，约 250KB） | `validate.py`(915行)、`regress.py`(2156行)、`tasktest.py`、`audit6.py`、`soci2.py`、`check-links.py` | 长期使用，但散在根目录 |

| 构建产物（未入库） | `kamloops.html`(2.1MB)、`open-subset.json`(128KB)、`err.log` | 已 gitignore，但和源码混在一起 |
| 早期一次性产物（**已入库**） | `tru-flyer.html`、`tru-flyer-ai-poster.png`(1MB)、`kamloops-welcome.pdf`(856KB)、`jesus-loves-you-flyer-a4.html`、`kamloops-newcomer-welcome-poster.html`、`kamloops_life_services_map_google_material_edition.html`、`Kamloops Life Services Map…A4 Portrait.pdf`、`logo.svg`、`kamloops-lifemap-qr.png` | 约 4MB，已被 `flyers/` 和 `docs/public/` 取代 |

另外：

- `tools/` 里放的恰恰是**一次性脚本**（`ingest-2026-09-10.py`、`history-2026-09-10.py`），
  而**长期脚本**（validate、regress、deploy）却在根目录——放反了。
- `flyers/` 把源码（`buildflyer.py`、`mapart.py`）和输出（5 个 PDF）混在一个目录。
- `outreach-emails-docx/`（127 个文件、9MB）在根目录，现已 gitignore，但位置上和其他外联材料脱节。
- `src/` 只有两个文件（`engine.html` + `data-kamloops.js`）——**这一处是对的**，
  "引擎不含城市事实"是这个项目的核心纪律，`validate.py` 会强制检查，不要动。

## 二、问题的实质

不是"文件多"，是**看不出哪些是承重墙**。一个新人（或半年后的你）打开根目录，
`regress.py` 和 `tru-flyer-ai-poster.png` 并排躺着，没有任何线索说明前者是每次提交都要跑的、
后者是三周前的一次性产物。项目继续迭代、尤其是**扩展到第二个城市**时，这会直接变成成本。

## 三、建议的目标结构

```
项目根/
  README.md  CHANGELOG.md  .gitignore
  wrangler.toml  worker.js          # 部署约定，必须在根
  build.py  deploy.sh               # 最常用的两条命令，留在根
  src/                              # 引擎 + 每城一份数据（不动）
  public/                           # 唯一会上云的目录（不动）
  docs/                             # 已整理完（不动）
  scripts/                          # 长期脚本，按用途分
    validate.py  check-links.py  export-open.py
    analytics/    query-events.py  analyze-events.py
    data/         addrecs.py  complex.py  fixcoords.py  themes.py
    monthly-quality-check.sh
  tests/                            # 测试与审计
    regress.py  tasktest.py  audit6.py  soci2.py
  flyers/
    buildflyer.py  mapart.py        # 只留源码
    out/                            # 生成的 HTML/PDF（gitignore）
  build/                            # 所有构建产物（gitignore）
    kamloops.html  open-subset.json  *.log
  docs/archive/assets/              # 早期一次性海报/传单，留档
```

## 四、分三步做，风险从低到高

**第一步：清理（几乎零风险，随时可做）**

1. 删掉入库的临时文件：`_changelog_entry_tmp.txt`、`COMMIT_MSG_v13f.txt`，
   并在 `.gitignore` 加 `COMMIT_MSG*`、`_*_tmp.txt`、`err.log`。
2. 把 9 个早期一次性产物（约 4MB）移进 `docs/archive/assets/`。
   它们已被 `flyers/` 和 `docs/public/` 取代，但记录了视觉演变，建议留档不删。
3. 建 `build/`，把 `kamloops.html`、`open-subset.json`、`err.log` 挪进去，改两处脚本的输出路径
   （`build.py` 的输出名、`export-open.py` 的输出名），`.gitignore` 相应改成 `/build/`。

做完这一步，根目录从 28 个文件降到约 12 个，且每一个都说得出用途。

**第二步：脚本归位（中等风险，建议在下次要动这些脚本时顺手做）**

把 6 个测试脚本移进 `tests/`、其余长期脚本移进 `scripts/`。
**风险点**：这些脚本大多用相对路径读 `src/data-kamloops.js`，移动后**仍须从项目根运行**
（`python3 tests/regress.py`）。`tools/monthly-quality-check.sh` 用的是 `$HERE`（脚本自身目录），
移动后必须改成项目根，否则会往错误的位置写 `data/*.log`。`deploy.sh` 里有一份敏感路径探针清单
（含 `data/business-hypothesis.md`），也要跟着核对。
每移一个就跑一次，别批量移完再测。

**第三步：拆分回归套件（收益最大，但是改代码不是搬文件）**

`regress.py` 2156 行、一次跑 12 分钟，资源紧张时会静默死掉（2026-09-10 的清单里已经提过）。
建议拆成 `tests/regress_fast.py`（3 分钟，每次改动跑）和 `tests/regress_full.py`（提交前跑）。
这件事和目录无关，但它是目前最影响迭代速度的一处。

## 五、建议**不要**做的

- **不要动 `src/` 的两文件结构**。它看着简陋，但"引擎里不许有城市事实"这条纪律是靠它成立的。
- **不要把 `public/` 当普通目录用**。放进去的东西会原样公开（`docs/guides/` 里的埋点手册记过这条红线）。
- **不要现在就为"多城市"预建目录**（`src/kelowna/` 之类）。第二个城市真正落地时，
  数据文件命名约定（`data-<city>.js`）已经够用，提前分层只会增加没人维护的空目录。
- **不要动 `data/`**。`tools/monthly-quality-check.sh` 往里写、`deploy.sh` 拿它当探针。

## 六、什么时候值得做

第一步随时可做，十分钟。第二、三步建议等到下面任一情况出现时再做，而不是专门排一次：

- 准备接第二个城市（那时结构不清的成本会立刻显性化）；
- 下次要大改 `regress.py` 或部署脚本时顺手；
- 有第二个人要参与这个项目。

在那之前，现在的结构**能用**——只是每次找东西要多花一点时间，而且这个成本会随迭代慢慢变大。
