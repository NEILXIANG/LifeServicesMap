## 阶段 1：城市配置化（第 2 周，约 4–5 天）⭐ 最关键

把所有"Kamloops"从引擎里拿出来，放进城市配置。

- [ ] 1.1 定义城市配置结构 `cities/<city>/city.json`：
  ```json
  {
    "id": "kamloops",
    "name": {"en": "Kamloops", "zh": "坎卢普斯", "...": "..."},
    "appTitle": {"en": "Kamloops Life Guide", "...": "..."},
    "region": "BC",
    "center": [50.67, -120.33], "zoom": 13,
    "bounds": [[..],[..]],
    "baseUrl": "https://kamloops-lifemap.neilxiang.workers.dev",
    "storagePrefix": "kamloops",
    "searchStopwords": ["kamloops", "bc"],
    "emergency": {...}
  }
  ```
- [ ] 1.2 engine 里 32 处逐一替换为读取 `CITY` 配置
- [ ] 1.3 localStorage 键统一为 `${storagePrefix}Xxx`
  - Kamloops 的 prefix 保持 `kamloops`，**现有用户的收藏 / 语言 / 任务进度零迁移**
  - 新城市自动得到独立键，互不干扰
- [ ] 1.4 搜索正则中的城市名改为从 `searchStopwords` 生成
- [ ] 1.5 `manifest.json`、`sw.js` 改为由 `build.py` 按城市生成（名称、CACHE 名、start_url）
- [ ] 1.6 `DATA_VERSION` 和 `sw.js` CACHE 由 `build.py` 自动生成（日期 + 内容哈希），不再手改

验收：`build.py --city kamloops` 产物与基线功能一致（regress 全过）；
`grep -ci kamloops src/engine.html` = 0。

## 节奏建议

| 周 | 阶段 | 产出 | 风险控制 |
|---|---|---|---|
| 1 | 0 准备 | CI、基线、CLAUDE.md | — |
| 2 | 1 配置化 | 引擎无城市硬编码 | regress 对比基线 |
| 3–4 | 2 拆分与 JSON 化 | 新目录结构 | 数据逐条比对 |
| 5 | 3 工具链 | 全部脚本支持多城市 | 测试城市 fixture |
| 6 | 4 部署统计 | 多城市部署 | 先部署到测试 Worker |
| 7–8+ | 5 Kelowna | 第二个城市上线 | 不改引擎即为成功 |

原则：
1. **每个阶段结束都能正常发布 Kamloops**。不做"大爆炸"重构，任何时候都能停下。
2. **每阶段一个 PR**，合并前对照基线跑全量测试。
3. **Kamloops 线上网址和用户本地数据不受影响**（localStorage 前缀沿用 `kamloops`）。
4. 每周固定半天做 Kamloops 数据维护，避免重构期间数据过期。
5. 工程（阶段 0–4）约 6 周、按每周 3–4 个工作日估算；可与 Kelowna 的外联和数据收集**并行**，第 7 周即可开始录入数据。

## 决策记录

以下四项原本需要 Neil 决定，2026-10-03 经授权由 Claude 按建议自主决定。

### D1 部署形态 — [自主决定] 方案 A：每个城市一个 Worker
- 决定：Kelowna 新建 Worker `kelowna-lifemap`（`kelowna-lifemap.neilxiang.workers.dev`），用 `wrangler.toml` 的 `[env.kelowna]` 区分；Kamloops 保持 `kamloops-lifemap` 不变。
- 理由：改动最小、城市之间互不影响、Kamloops 现有网址和二维码继续有效；免费额度足够。
- 保留退路：代码里线上网址、Origin 白名单、service worker 作用范围全部从 `city.json` 读取，以后切换到方案 B（一站多路径）或 C（自有域名）只改配置和 Worker 路由。
- 重新评估时机：上线第三个城市时，或者决定启用总品牌时。

### D2 总品牌与域名 — [自主决定] 暂不启用，先在代码里预留
- 决定：现在不买域名、不改对外名称，各城市沿用"<城市> Life Guide"。代码、配置、新文件命名一律使用中性名称（如 `lifeguide`），不再出现新的城市专属命名。
- 理由：品牌和域名要花钱，也会让 Kamloops 已发出去的宣传材料失效；在第二个城市验证有用户之前，投入不划算。
- 重新评估时机：Kelowna 上线 3 个月后，或者准备做第三个城市时。

### D3 Kelowna 城市范围 — [自主决定] Kelowna 市 + West Kelowna
- 决定：首期范围为 City of Kelowna 与 City of West Kelowna（含 Westbank First Nation 地区的公共服务点）。Lake Country、Peachland 暂不纳入，但地图边界 `bounds` 留出余量，以后只需加数据。
- 理由：这两地是新移民、留学生（UBC Okanagan、Okanagan College 都在 Kelowna 市内）的主要居住和办事范围；首期范围越小，越容易做到全部核实。
- 重新评估时机：首期核心数据完成后，或者当地合作方提出需要时。

### D4 运营资料是否移出代码仓库 — [自主决定] 移出工作目录，暂不改写 git 历史
- 决定：
  1. 阶段 0 把 `outreach-emails-docx/`、`flyers/` 的成品、`docs/public/` 的 PDF、`docs/outreach/` 移到仓库外的同级目录 `../Guide to Life in Canada - ops/`（建议放在 iCloud 等可同步的位置），仓库里只留一个 README 说明去向。
  2. 在 `.gitignore` 中重新排除这些目录。
  3. **不**改写 git 历史（`git filter-repo` 会改变全部提交号，属于不可逆操作，必须由 Neil 明确同意）。仓库目前是私有的，风险可控。
- 理由：外联邮件含联系人姓名和邮箱，属于个人信息；这些二进制文件也是仓库达到 95MB 的主要原因，多城市以后只会更多。
